# 用户管理

此页面用于维护平台用户账号、状态和基础资料。

## 页面用途

- 搜索并浏览用户列表。
- 新建或编辑用户。
- 重置密码、删除账号或执行代登录等维护动作。
- 查看用户的群组、状态和创建时间等关键信息。

## 你会看到什么

### 用户列表

- 用户名、昵称、邮箱。
- 状态、群组、创建时间等字段。
- 分页表格或移动端卡片，支持关键词和群组筛选。关键词可查找用户名、邮箱、姓名或用户 ID；用户 ID 没有单独的筛选框。
- “显示RAM角色”开关开启后筛选 RAM 子用户；关闭时默认排除 RAM 子用户。当前操作者不显示在列表中。
- 刷新会清除筛选并返回第一页。

### 管理动作

- 新建用户。
- 编辑用户（资料、状态）。
- 修改密码。
- 删除用户。
- 代登录或切换到目标用户视角。

## 常见操作

1. 先使用搜索或分页定位目标用户。
2. 打开编辑窗口修改基础资料或状态。
3. 在忘记密码或交接场景中使用重置密码功能。
4. 在有权限时使用代登录进行问题复现或协助。

## 层级限制

操作受以下规则约束：

- 只能管理**等级高于自身**的用户（群组等级数值更大）。
- 不能修改或删除与自身同级或更高级别的用户。
- 不能删除自己。

## 删除说明

删除会将账号标记为已删除并释放原用户名；不要将此操作视为清除所有关联业务数据。删除操作会记录到**业务日志**。删除前请确认目标账号及其关联资源。

## 所需权限

| 操作                   | 所需权限                                                          |
| ---------------------- | ----------------------------------------------------------------- |
| 查看用户               | `USER_READ`                                                       |
| 新建用户               | `USER_CREATE`                                                     |
| 编辑用户（资料、状态） | `USER_UPDATE`                                                     |
| 删除用户               | `USER_DELETE`                                                     |
| 修改他人密码           | `USER_CHANGE_OTHERS_PASSWORD`                                     |
| 代登录用户             | `USER_IMPERSONATE_VIEW` 或 `USER_IMPERSONATE_ACT`（满足其一即可） |

修改他人密码时，已启用 2FA 的操作者可能需要完成二次验证；受信任窗口内可按当前安全规则通过。

## 用户目录读取的资源权限

IAM 强制模式下，用户目录列表使用 `quyan:user:ListUsers`，详情使用 `quyan:user:GetUser`，每个受管用户对应 `acs:platform:*:platform:user/<用户ID>`。两项操作均要求当前主体属于具有 `USER_READ` 的有效平台全局组，个人附加权限、账户私有组和账户所有者身份不能替代这一资格。账户 RAM 子用户管理仍使用自己的账户资源和操作。

列表保留原有组等级可见范围及 RAM 用户筛选，再剔除被策略拒绝的用户，之后计算总数、分页和 `hasMore`，只读取获准页面的数据。列表权限不会自动授予详情权限。禁用用户仍可用于账户管理，已删除用户退出这些读取范围。不存在或被拒绝的详情返回通用授权错误，不返回资料或余额。

每页最多 100 人，页码最多 10,000。读取期间资料、归属、余额、组显示信息、列表资格、策略或角色会话变化时，请求被拒绝。响应保持现有资料字段，不包含密码和权限数组。AssumeRole 使用角色授权，不继承操作者全局组的 Allow；已认证 AccessKey 使用相同资源检查。

IAM 授权同时检查账号主用户是否有效。主用户被禁用或删除后，即使子用户自身仍启用，其 JWT、已认证 AccessKey 和 AssumeRole 会话也不能继续通过 IAM 授权。普通账号主用户与超级管理员主用户遵循同一有效状态要求。

## 资源级删除用户

IAM 强制模式下，`quyan:user:DeleteUser` 授权目标资源 `acs:platform:*:platform:user/<userId>`，并要求操作者所在有效全局管理组具有用户删除资格。不能删除自己、当前账号的主用户或同级、更高等级的用户；被禁用的用户仍可按相同限制删除。

删除会把用户标记为已删除并释放原用户名。目标数据、等级、策略或角色会话在授权与提交之间变化时，请求被拒绝；提交前授权或条件复核失败会回滚状态和用户名。删除不需要同时具备列表或详情读取权限。`legacy` 和 `shadow` 模式保留原删除权限检查，影子评估不执行第二次删除。

## 资源级用户模拟

IAM 强制模式下，用户模拟按目标用户资源 `acs:platform:*:platform:user/<userId>` 授权：

- `quyan:user:StartViewImpersonation`：签发只读模拟会话。
- `quyan:user:StartActImpersonation`：签发允许操作的模拟会话。

这两项权限分别要求操作者所在的有效全局管理组具备对应模拟资格。个人附加权限、私有组或单独的策略 Allow 不能替代这项资格。目标必须是有效用户，权限等级低于操作者；不能模拟自己或在模拟会话中再次发起模拟。

系统优先使用获准的操作模式；只有只读模式也获准时，才可改用只读模式。只读会话禁止写请求。模拟 Token 有效期为一小时，不签发 Refresh Token。

每次使用或跨站恢复模拟会话时，系统重新检查原操作者、目标等级、对应 Action、资源、条件和策略。权限撤销后，已有操作会话会被拒绝，不会自动降为只读模式继续使用。角色会话撤销或过期、AccessKey 禁用或过期、操作者被强制下线，也会阻止相关模拟会话继续使用。AssumeRole 只使用当前角色的授权，不能继承操作者全局组的 Allow。

切换到 IAM 强制模式后，切换前签发且未携带原授权主体信息的模拟 Token 需要重新发起模拟。`legacy` 和 `shadow` 模式保留旧权限检查与模拟行为；`shadow` 会比较新的资源级检查，但只签发一次 Token。

## 资源级用户更新

IAM 强制模式下，更新用户按 `acs:platform:*:platform:user/<userId>` 授权，并要求操作者所在的有效全局组具备用户管理资格：

| 修改内容     | 所需 Action                           |
| ------------ | ------------------------------------- |
| 用户资料更新 | `quyan:user:UpdateUser`               |
| 邮箱字段     | 同时需要 `quyan:user:SetUserEmail`    |
| 状态字段     | 同时需要 `quyan:user:SetUserStatus`   |
| 用户组字段   | 同时需要 `quyan:user:AssignUserGroup` |

换组权限必须同时覆盖目标用户 ARN 和 `acs:platform:*:platform:group/<groupId>`。目标组须为有效全局组，或属于目标用户的实际账户。系统检查新组的策略、范围授权及角色权限；普通操作者只能转授自己已被授权的范围，不能提高目标的权限等级，也不能通过移除原组的 Deny 扩大权限。系统配置的真实全局管理员主账号可执行受控的恢复授权，但仍需满足对应 Action，匹配的显式 Deny 仍会阻止操作。替换其他账户所有者的用户组时，还必须保留其已有 IAM 恢复权限，不能为其引入组策略或组角色中的 Deny。

除修改自己的姓名等普通资料外，该接口不能为操作者自己或当前账户所有者换组、修改恢复邮箱或禁用账户。自己的邮箱应使用账户设置中的验证流程。被禁用的目标可更新资料，并在具备独立状态权限时启用；同级及更高权限用户不可被普通跨用户更新操作修改。

授权、目标资料、所属组、角色会话及相关策略会在事务中复核。复核失败时，本次姓名、邮箱、状态和组变更全部回滚。`legacy` 与 `shadow` 保留旧权限强制检查，影子评估只比较授权结果，不额外执行更新。

## 资源级用户创建

IAM 强制模式下，创建用户需要 `quyan:user:CreateUser` 同时覆盖两个资源：

- 用户目录：`acs:platform:*:platform:user-directory`。
- 创建后由系统生成的用户：`acs:platform:*:platform:user/<userId>`；预先授权可使用 `user/*`。

操作者必须属于具备用户创建资格的有效全局管理组。创建出的用户为独立主账号，不能通过请求指定其 ID、所属账户或个人附加权限。密码继续使用既有加密传输和服务端哈希流程，响应不返回密码。

指定用户组时，还需 `quyan:user:AssignUserGroup` 同时覆盖新用户和 `acs:platform:*:platform:group/<groupId>`。新账号只能加入有效全局组；普通操作者不能创建同级或更高权限用户，也不能转授自己没有的权限。系统配置的真实全局管理员主账号可执行受控的恢复创建，但角色会话不能使用该例外，显式 Deny 仍然生效。创建资格不会自动赋予更新已有用户的资格。

未指定组时，系统使用普通注册组。只有该组仍保持系统预设的确切基础权限时，创建流程才可直接授予这些基础权限；额外组权限、策略和角色权限仍需通过委派检查。显式指定同一个组也需完整的组授权和委派检查。

系统先检查目录权限，在事务生成真实 ID 后再次检查用户资源及组权限。授权或组配置变化、资源被拒绝时，创建会完整回滚。`legacy` 和 `shadow` 保留旧权限强制检查；`shadow` 检查旧流程实际创建的 ID，不额外创建用户。

## 说明

- 删除或禁用用户前，建议先确认其余额、权限和关联资源。
- 代登录属于高权限操作，应仅用于运维或客服协助。
- 批量排查问题时，可配合权限页与业务日志页一起使用。
