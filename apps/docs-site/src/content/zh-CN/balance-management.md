# 余额管理

余额管理用于查询用户余额、手工增加或扣减余额，以及核对交易流水。手工调整会直接改变用户的站内余额，请先确认用户 ID、金额和调整原因。

## 账户数据与可超额额度

拥有 `BALANCE_MANAGEMENT_READ` 权限时，本页显示平台账户管理界面；只有旧 `BALANCE_READ` 权限时，继续显示原余额管理界面。新界面按服务端分页，支持完整用户 ID 搜索；没有余额账户的用户显示零值。

新界面需要部署管理的全局用户组授予对应能力。读取账户需要 `BALANCE_MANAGEMENT_READ`，修正数据需要独立的 `BALANCE_ACCOUNT_ADJUST`，修改超额规则需要独立的 `BALANCE_OVERDRAFT_MANAGE`。IAM 策略还可限制具体用户，旧的余额读取或充值权限不会自动获得这些能力。写入会执行权限复核、重放保护和已配置的二次验证。

### 设置默认规则或用户规则

1. 在“默认超额规则”设置金额算法、上下限和允许使用额度的消费类别，然后保存。初始规则为禁止超额；初始类别为 API 中转和网页聊天，禁止超额时类别不会授予额度。
2. 默认规则动态作用于所有继承用户，包括已有用户。列表中的“超额规则”可为单个用户独立覆盖规则和类别，或分别恢复继承。
3. 批量设置将跨页勾选的用户显示为可删除的用户名标签。也可输入用户名并按回车添加，或粘贴以空格、换行、逗号分隔的多个用户名；自动去重，支持逐项删除或清空，每批最多 200 人。规则与类别分别选择保持不变、独立覆盖或继承默认。
4. 先试算，核对用户名、累计充值、可超额额度和剩余额度，再确认保存。用户名不存在或无权操作时不会提交整批修改。更改标签或其他输入会使原试算失效。保存绑定试算已确认的账户；账户规则或默认版本已变化时整批拒绝，请刷新后重新试算，批量保存不会只成功一部分。

| 算法         | 可超额额度的基础值                      |
| ------------ | --------------------------------------- |
| 禁止超额     | 始终为零，不应用保底                    |
| 固定额度     | 固定金额                                |
| 充值百分比   | 累计充值 × 百分比 ÷ 100                 |
| 固定加百分比 | 固定金额 + 充值百分比金额               |
| 取大 / 取小  | 固定金额与充值百分比金额的较大 / 较小值 |
| 自定义公式   | 按受限算术表达式计算                    |

除禁止超额外，计算结果再应用最低额度和可选最高额度，按四位小数向下取整。累计充值使用现有统计，包含支付充值、兑换、收到的转账和计入统计的管理员入账，退款会减少该统计；它并非仅指现金实付充值。

公式变量为 `totalRecharged`（累计充值）、`totalUsed`（累计消费）、`fixedAmount`（固定金额）和 `percent`（百分数，10 表示 10%）。支持 `+ - * /`、括号、`min`、`max`、`abs`、`round`；`round` 按四位小数四舍五入。例如 `min(100, fixedAmount + totalRecharged * percent / 100)`。不支持脚本、属性访问或其他函数；除零、结果超出金额范围、过长或过深的公式会被拒绝。统计变化导致已有公式失效时，可超额额度按零处理，并显示计算失败。

### 消费范围与共享额度

可单独允许 API 中转、网页聊天、开发者按量服务、OJ 提问、月卡购买、拼车和终端购买使用超额额度。各类别共享同一份额度，不会分别发放。已用额度为负余额的绝对值，剩余额度最低为零；充值或统计修正会重新影响额度。

AI 请求在开始前检查该类别的余额加可超额额度是否大于零；获准请求按实际用量完整结算，可能暂时超过额度，后续请求将被拦截。月卡覆盖仍按原规则执行。已知金额的购买必须在考虑其他拼车预留后仍不低于允许的负余额。转账、礼品码转出与原路支付退款不能使用超额额度。

### 独立修正余额、累计充值和累计消费

1. 选择“修正账户数据”，仅勾选需要修改的字段。修改余额不会自动修改累计统计，修改累计充值也不会给余额入账。
2. 每个字段可选择增减差额或设定目标值。累计充值与累计消费不得为负；金额最多四位小数，绝对值不得超过 999999.9999。
3. 填写原因并试算，查看修改前后的账户数据、可超额额度与剩余额度。输入改变后需要重新试算。
4. 确认后写入账务流水和业务日志，即使只修改统计、余额差额为零也会留痕。目标值写入要求原字段值仍与读取时一致，否则拒绝；差额写入在最新账户值上累加。

同一弹窗中未修改内容的失败重试沿用操作编号，服务端避免重复入账。重新打开弹窗或更改内容属于新的操作；网络结果不明时，先刷新账户与日志核对。试算不锁定未来余额，提交时仍会检查当前数据、权限和金额范围。

新界面中的原“调整余额”和“查看历史”仍使用旧权限与账号资源范围：前者提交差额，可选择是否计入统计；后者按服务端分页查看最近 30 天的获准流水。原有账号范围不会因新增平台管理权限而扩大。以下旧界面操作说明适用于仅使用原余额管理功能的用户。

## 支付宝订单与原路退款

页面的“支付宝订单与退款”区域使用独立的 `PAYMENT_READ` 权限；页面本身仍要求原有余额管理权限。可按用户 ID 查询订单，核对人民币金额、到账额度、支付宝交易号、状态和退款记录，订单及退款记录均支持分页。

发起退款还需要 `PAYMENT_REFUND` 权限，启用了两步验证的账户需完成验证。选择已支付订单的“原路退款”，填写人民币退款金额和原因；默认金额为剩余可退金额。可以多次部分退款，累计不能超过实付金额，同一订单有退款处理中时不能发起新退款。

退款按下单时的充值比例扣回账户额度，服务端会检查扣除拼车预留后的可用余额。余额不足时拒绝退款，不允许因退款新增欠款。处理中先扣留额度；退款成功后保留扣回结果，支付宝明确拒绝时返还额度。网络超时或结果不明时保留处理中，使用退款记录中的刷新按钮或等待后台补查。不要通过人工加减余额代替退款确认。

退款成功会减少累计充值额度，不计作用户消费。退款手续费和退款资格以支付宝签约及交易状态为准；已完结、超过可退期限或支付宝限制部分退款的订单可能无法退款。

## 使用前提

进入页面需要 `BALANCE_READ`。页面还会读取用户目录，因此需要相应的用户读取权限；调整需要独立的 `BALANCE_RECHARGE`。启用两步验证的账号提交调整时，可能需要完成二次验证。

IAM 强制模式下，余额和交易查询受账号归属及资源授权约束。能在用户目录看到某个人，不代表有权读取或调整其余额，详见下文。

## 查询用户余额

1. 在 **用户 ID** 中填写目标用户的完整 ID，单击 **搜索**。
2. 核对列表中的用户 ID、用户名、当前余额和更新时间。列表每页 20 人，可通过分页继续查看。
3. 保留筛选重新查询时，单击 **搜索**。**刷新** 会清空用户 ID 并返回第一页。

列表没有返回余额账户时会显示 0，并使用当前时间作为更新时间。这个时间不能证明账户刚发生变动，0 也不能单独证明已有余额账户被清空。本页不显示拼车预留金额，不能把显示余额直接当作全部可转出金额。

读取失败时旧列表可能仍保留，请先处理错误并重新查询，再进行调整。

## 增加或扣减余额

1. 在目标用户行单击 **调整余额**，再次核对用户 ID 和当前余额。
2. 填写 **金额**：正数增加，负数扣减，不能为 0；单次范围为 -100000～100000，最多 4 位小数。也可填写 **增减后余额**，页面会按当前显示余额计算差额。
3. 核对 **计入统计**。默认开启，增加计入累计充值，扣减的绝对值计入累计花销；关闭后仍会变更余额并保留交易流水，只是不增加这两项累计统计。
4. 填写调整原因，便于后续核对；最多 500 字符。留空时页面使用默认的管理员充值或扣减说明。
5. 单击 **确认** 并完成页面要求的验证。成功后对话框关闭，列表重新加载；单击 **查看历史** 核对调整流水和实际余额。

**增减后余额是估算值，提交的是差额。** 例如窗口中余额为 10，目标设为 15，提交金额为 +5；如果提交前另一次消费已把余额变成 8，调整后将为 13。需要精确核对时请刷新后重新计算，不能把该字段视为锁定目标余额。

手工扣减没有“余额不足则拒绝”的保底，可能产生负余额。提交前请核对扣减后结果；已有拼车预留或并发消费时还应核对相关订单。重复提交同一差额会再次增减余额，页面没有撤销按钮。需要更正时，先确认原流水，再按实际差额创建一笔说明清楚的新调整。

## 查看交易历史

1. 在用户行单击 **查看历史**。默认加载该用户最近 7 天的获准记录。
2. 根据需要选择最近 1 天、7 天、30 天，或 **加载全部**；加载全部需要确认。
3. 在已加载数据中按交易类型、Token、渠道、模型或时间筛选，核对金额、变动前后余额和说明。可切换表格与图表查看。
4. 查看新交易时单击历史窗口中的 **刷新**；需要重新按时间范围加载时，重新选择加载范围。

服务器仅返回最近 30 天内的有效流水，**加载全部不会取得更早的完整账本**。历史窗口中的日期和其他筛选只过滤已加载数据，不会自动补查范围外记录。图表和记录数也仅基于当前已加载、获准且经过筛选的记录，不能代替账户全生命周期统计。

历史刷新会追加自上次加载以来的新记录，不会重新计算或裁剪原时间范围。增量刷新失败可能没有单独提示；需要确认最新数据时重新选择范围。范围加载失败时应先处理错误，不要将旧记录或空列表当作最新查询结果。

## 权限与资源范围

| 任务                   | 所需权限           |
| ---------------------- | ------------------ |
| 读取页面使用的用户目录 | `USER_READ`        |
| 查看余额和交易记录     | `BALANCE_READ`     |
| 增加或扣减余额         | `BALANCE_RECHARGE` |

IAM 强制模式下，用户目录使用 `quyan:user:ListUsers` 和部署共享的 `acs:platform:*:platform:user/<userId>` 资源，并需要部署管理全局组的用户读取资格。余额和流水则按当前账号归属授权，仅可处理同一账号内的有效用户；为其他账号写一条 Allow 不会改变其归属。

下表中的 `accountId` 是当前账号 ID。

| Action                               | 资源 ARN                                                         |
| ------------------------------------ | ---------------------------------------------------------------- |
| `quyan:balance:GetUserBalance`       | `acs:quyan:*:<accountId>:user/<userId>`                          |
| `quyan:balance:RechargeUserBalance`  | `acs:quyan:*:<accountId>:user/<userId>`                          |
| `quyan:balance:ListUserTransactions` | `acs:balance:*:<accountId>:transaction/<userId>/<transactionId>` |

读取和调整分别授权。页面按当前用户列表批量读取余额，任一目标不在账号范围内或未获准时，整次余额查询可能失败，而不是自动跳过。此时可按一个有权管理的用户 ID 缩小查询，并请管理员检查用户目录与余额范围是否一致。

交易列表只统计和分页获准流水；当前没有可见记录不代表该用户没有消费。角色会话失效、账号状态或权限在请求期间改变时，需要重新登录或刷新后再核对。

## 常见问题

| 现象                           | 处理建议                                                       |
| ------------------------------ | -------------------------------------------------------------- |
| 页面可见，但列表加载失败       | 分别检查用户目录权限、当前页所有用户的余额读取权限和账号归属   |
| 目标余额与提交后余额不同       | 检查差额、并发消费或其他调整，以交易流水中的变动前后余额为准   |
| 关闭计入统计后仍有流水         | 这是正常行为；该开关只控制累计充值和花销，不隐藏余额变动       |
| 调整后连接中断，不确定是否成功 | 先重新搜索用户并查看历史，确认原操作结果后再决定是否提交新调整 |
| 加载全部后仍无较早记录         | 服务端仅查询最近 30 天，局部日期筛选无法扩大该范围             |
