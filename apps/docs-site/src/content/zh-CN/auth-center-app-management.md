# 认证中心应用接入

认证中心向已注册的接入系统签发 RS256 签名的 JWT 访问令牌。接入系统通过可信 JWKS 验证签名和声明，再执行自己的业务授权；需要延长用户会话时，使用刷新令牌向认证中心换取新令牌。

## 选择接入方式

| 场景                                 | 应用与授权类型                                                  | 令牌结果                                 |
| ------------------------------------ | --------------------------------------------------------------- | ---------------------------------------- |
| 有可信后端的网站，用户登录或同意授权 | 机密应用，`authorization_code`，按需启用 `refresh_token`        | 用户 JWT；启用刷新授权时同时签发刷新令牌 |
| SPA、移动端或桌面程序，无法保管密钥  | 公开应用，`authorization_code` + PKCE，按需启用 `refresh_token` | 用户 JWT；公开应用没有 Client Secret     |
| 后台服务、定时任务，无用户参与       | 机密应用，`client_credentials`                                  | 应用 JWT，不签发刷新令牌                 |

认证中心应用、凭据和令牌与[普通 OAuth 应用](/zh-CN/oauth-app-management)分别管理。认证中心 JWT 供已配置验证的接入系统使用；不要默认它可以代替平台登录令牌或普通 OAuth 令牌访问平台业务 API。

## 接入前准备

1. 在[认证中心应用管理](/zh-CN/auth-center-client-management)创建应用，配置客户端类型、最小授权类型、Scope、回调和令牌有效期。
2. 创建机密应用后立即保存 Client Secret，再提交审核。只有 `approved` 应用可以授权、兑换或刷新令牌。
3. 向部署管理员确认实际 API 源地址、准确 issuer、JWKS 地址，以及用户流程所需的授权界面地址。
4. 明确接入系统接受的 Client ID、所需 Scope、用户或应用身份，以及撤销后的访问控制方式。

本平台的认证中心授权预览及决定是需要平台登录身份的 API。接入部署需要提供调用这些 API 的授权界面。内置 `/oauth/authorize` 页面调用的是另一套普通 OAuth 接口，不能直接作为认证中心入口。

## 完成授权和令牌获取

### 用户授权码流程

1. 接入应用生成随机 `state` 和 PKCE verifier，以 S256 计算 challenge。公开应用必须使用 PKCE；机密应用也建议启用。
2. 将用户带到部署提供的授权界面，传入 Client ID、精确登记的回调、所需 Scope、state 和 challenge。
3. 授权界面以用户的平台登录身份调用授权预览，再根据用户明确选择提交同意或拒绝。成功响应提供 `redirectTo`，由界面执行跳转。
4. 接入应用在回调中核对同一授权尝试的 state，再向令牌接口发送授权码、回调、verifier 和客户端信息。机密应用需要密钥，公开应用不发送密钥。
5. 验证收到的 JWT，再建立自己的用户会话。授权码有效期为 5 分钟且成功兑换后不能重复使用；失败或结果不确定时重新开始授权。

应用获准申请 Scope 不等于用户已经同意。用户同意和当前可授予范围仍需检查；拒绝授权时，回调包含错误信息而不是授权码。回调必须匹配登记值，包含协议、域名、端口、路径和末尾斜杠。

### 机器间调用

机密应用启用 `client_credentials` 并审核通过后，由服务端使用 Client ID 和 Client Secret 请求令牌，按需提交空格分隔的 Scope。访问令牌代表应用自身，不能当作终端用户已登录。令牌到期后重新申请，不使用刷新令牌。

### 刷新与撤销

启用 `refresh_token` 还必须启用 `authorization_code`。刷新成功会签发新的访问令牌和刷新令牌，并撤销已使用的刷新令牌。接入方需安全替换旧值并协调并发刷新；有效 Scope 仍受用户授权及应用当前允许范围限制。

使用 `POST /v1/auth-center/revoke` 撤销不再需要的令牌，提交令牌及该客户端所需的认证信息。撤销请求针对提交的令牌；不要把撤销一个访问令牌当作同时撤销所有刷新令牌。计划删除应用时，应先完成需要的撤销。

## 端点与响应格式

以下路径位于部署提供的 API 源地址下，请先确认实际代理路径可以访问。

| 方法和路径                                             | 用途                       | 响应与身份要求                                                                                                   |
| ------------------------------------------------------ | -------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `GET /v1/auth-center/.well-known/openid-configuration` | 获取发现信息               | 公开读取，业务包装 `{ code, message, data }`                                                                     |
| `GET /v1/auth-center/.well-known/jwks.json`            | 获取验签公钥               | 公开读取，公钥集合位于 `data.keys`                                                                               |
| `GET /v1/auth-center/authorize`                        | 获取授权预览               | 需要平台登录身份及预览操作授权，返回业务包装                                                                     |
| `POST /v1/auth-center/authorize`                       | 提交用户决定               | 需要平台登录身份及决定操作授权，回调地址位于 `data.redirectTo`                                                   |
| `POST /v1/auth-center/token`                           | 授权码兑换、刷新或机器授权 | JSON 请求，成功时直接返回 `access_token`、`token_type`、`expires_in`、`scope` 及按授权类型返回的 `refresh_token` |
| `POST /v1/auth-center/revoke`                          | 撤销指定令牌               | 客户端认证，成功时直接返回 `{ revoked: true }`                                                                   |

发现文档根据配置的 issuer 拼接 `authorization_endpoint`、`token_endpoint` 和 `jwks_uri`，地址可能不同于上述公开路由。由管理员确认代理映射；不能访问时，使用部署提供的实际端点，JWT 验证的 issuer 仍单独使用管理员给出的准确值。若发现信息与签发配置不一致，应修正部署配置，不要关闭 issuer 校验。

标准库若要求原始 JWKS，需要先检查 HTTP 和数字 `code: 0`，再将 `data` 中的公钥集合交给验证器。令牌接口则必须先检查 HTTP 成功状态和有效令牌内容；失败响应也可能包含 `access_token` 等字段，不能仅因字段存在就视为成功。发现路径名不表示会签发 ID Token，当前令牌响应不包含 `id_token`。

## 在接入系统验证 JWT

1. 从预先配置的可信地址获取并缓存 JWKS，按令牌头部 `kid` 选择公钥；未知 kid 时刷新可信公钥集合，仍找不到则拒绝令牌。
2. 允许算法固定为 RS256，验证签名、过期时间、准确 issuer 和预期 audience。audience 是签发令牌的应用公开 Client ID，不能从请求者提交的值直接决定。
3. 验证 `token_use` 为 `access_token`，并按业务要求检查 Scope、授权类型及身份。用户流程的 `sub` 是用户标识，包含 `uid`；机器流程的 `sub` 是 Client ID，不包含用户身份。
4. 根据验证后的身份执行接入系统自己的权限判断。只解码 JWT 或验签成功都不足以授予所有业务权限。

仅靠本地验签不能实时知道服务端已撤销令牌、应用已删除或账户已停用。根据访问风险选择有效期和接入方的额外访问控制；密钥轮换、删除应用或退出控制台都不能保证所有本地验证器立即拒绝旧 JWT。

## 常见问题

| 现象                                 | 排查方向                                                                      |
| ------------------------------------ | ----------------------------------------------------------------------------- |
| 发现端点返回的数据无法交给标准库     | 检查业务包装，提取 `data`；确认发现信息中的 URL 通过部署代理可访问            |
| 访问授权地址只得到 JSON 或未登录错误 | 该地址是 API，需要部署提供的授权界面及平台登录身份                            |
| 兑换或刷新被拒绝                     | 检查 `approved` 状态、允许的授权类型、密钥、回调、PKCE 及令牌是否已使用或过期 |
| JWT 验签或 issuer、audience 检查失败 | 核对可信 JWKS、kid、RS256、准确 issuer 和本应用 Client ID，不要跳过失败项     |
| 机器令牌没有刷新令牌                 | `client_credentials` 只签发访问令牌，到期后重新申请                           |
| 撤销后接入系统仍接受 JWT             | 本地验签无法读取服务端撤销状态，检查有效期及接入方的访问控制策略              |
